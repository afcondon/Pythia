# 0003. Two implementations: `purepy` the oracle, `backend-py` the optimizer consumer

- Status: Accepted
- Date: 2026-07-31

## Context

Gate B4 — running the compiler's own `tests/purs/passing` corpus — left Pythia
at 341/347, with a residue that is **not** a list of small independent defects.
Four of the six causes are shared with Jurist and Gnomon, and the largest is
**TCO**: [0002](0002-expression-emission-lambda-lifting.md)'s trampoline handles
self-recursion, and mutual and partial tail calls escape it (`TCOMutRec`,
`PartialTCO`, `3957`).

Reading the mature non-JS backends produced an inversion worth restating here,
because it changes what "prior art" means for this repo. purerl,
`purescript-lua`, purescm and `backend-wasm` all target runtimes with **native
proper tail calls**, so none of them ever solved this — `grep -rn trampolin`
finds nothing in purerl or `purescript-lua`. Python has no TCO, which leaves
**JavaScript** as the only comparable case, and
`purescript-backend-optimizer` has solved it in `Codegen/Tco.purs`: a
`TcoRole { joins, isLoop }` analysis that collapses a mutually-recursive group
into a single loop with join-point dispatch.

The alternative was hand-porting that analysis into three separate Haskell
generators. `TCOMutRec` also asserts the ES backend's exact TCO **frontier** —
it requires that certain shapes *do* overflow — so three hand-ports would be
three chances to drift from a boundary the corpus checks byte-for-byte.

## Decision

Add a **second implementation** in this repo: `backend-py/`, a PureScript
program consuming `purescript-backend-optimizer`'s `BackendSyntax`/`NeutralExpr`
IR and lowering it to Python. It is **additive**. `purepy` (Haskell, raw CoreFn)
stays, and stays the correctness **oracle**.

This mirrors Gnomon's ADR-0007 and extends the family decision recorded in
`docs/kb/architecture/adopt-backend-optimizer-family-wide.md` (the `docs` repo).

Three properties make it worth having two:

**1. The oracle is the honesty layer.** A single implementation cannot check
itself. Running both lanes over the same corpus and diffing them is what makes
"conformant" a checkable claim rather than a hope.

**2. One runtime, shared, not forked.** `backend-py` emits one Python file per
PureScript module using `purepy`'s own naming, so `_purepy_runtime.py` and every
`<Module>_foreign.py` are produced by `purepy` and consumed unmodified. Neither
is generated by `backend-py` and neither is checked in beneath it. This is a
direct response to evidence: Gnomon kept two ~2,400-line Go runtimes, they
silently diverged by two symbols, and it took a red CI and a symbol-set diff to
notice (2026-07-31). Here the divergence is not merely discouraged, it is
structurally unavailable.

**3. Statement-oriented emission**, which is the substantive difference from
`purepy`. This is not a stylistic preference — see Consequences.

## Consequences

**Measured on the shared differential corpus, 2026-07-31: 20/20 green**
(17 byte-identical to the JavaScript reference, 3 ledger-only) —
`backend-py/run_conformance.sh`.

**Measured on `tests/purs/passing` @ v0.15.15, both lanes run the same day with
the same harness** (`purs-corpus/run_corpus.py`):

```
purepy      341/347 = 98.3%     (the oracle)
backend-py  343/347 = 98.8%     (this lane)
```

Every test on which the two differ:

| test | `purepy` (oracle) | `backend-py` (optimizer) | why |
|---|---|---|---|
| `3957` | ✗ `RecursionError` | **PASS** | TCO |
| `PartialTCO` | ✗ `RecursionError` | **PASS** | TCO |
| `StringEscapes` | ✗ lone surrogate | **PASS** | string literals |
| `BigFunction` | ✗ `SyntaxError: too many nested parentheses` | **PASS** | statement emission |
| `NegativeIntInRange` | PASS | ✗ `CODEGEN_ERR` | upstream decoder |
| `StringEdgeCases` | PASS | ✗ `CODEGEN_ERR` | upstream decoder |
| `2136` | ✗ | ✗ | `Int` wrapping |
| `TCOMutRec` | ✗ | ✗ | join points |

Four fixed, two regressed, two shared: 341 + 4 − 2 = 343. The regressions are
stated plainly because they are the price of the lane, and both are **upstream
in `purescript-backend-optimizer`'s CoreFn JSON decoder**, not in this lowering:

- `NegativeIntInRange` is `n = -2147483648`. `purs` emits that as
  `Data.Ring.negate` applied to `IntLiteral 2147483648` — verified by reading
  the CoreFn, not inferred from the message — and `decodeInt` rejects the
  literal because `Int.fromNumber` sees it outside the `Int32` range. The
  literal really is out of range; the *expression* is not, which is the whole
  point of the test's name.
- `StringEdgeCases` carries a lone surrogate, which `purs` emits as an array of
  code units. `decodeStringLiteral` handles that form; some other field on the
  path is decoded with plain `decodeString`, which does not.

`2136` is untouched and always will be: `Int` wrapping is a *representation*
decision in the lowering, not an IR decision. It needs the Gate C9 answer, and
the same answer on all three backends.

`4174` and `ShadowedModuleName` pass on **both** lanes: the oracle's
module-shadowing fix landed the same day, so they no longer separate the two.

**Statement emission is what retires `BigFunction`.** [0002](0002-expression-emission-lambda-lifting.md)
records the wall this repo hit — CPython caps parenthesis nesting at ~200 — and
answers it with lambda lifting, because an expression-oriented emitter has no
other move: a lambda's body is textually inside every enclosing call.
`backend-py` does not have the problem to solve. A `Let` is an assignment, a
`Branch` is an `if`/`elif` chain, an `EffectBind` chain is a flat run of
statements, and only real lexical nesting costs indentation. No lifting pass,
and no `_mk` re-currying.

**Two toolchains in one repo.** Haskell/stack for `purepy`, PureScript/spago for
`backend-py`. Gnomon already lives with this. `backend-py` is 1,332 lines
against `purepy`'s 2,474: a consumer costs roughly what a hand-written
generator costs, and the win is not less code — it is not re-solving TCO,
inlining and dead-code elimination three times.

**A moving upstream dependency**, pinned through the package set.

### Four hazards that statement emission introduces, and how each is handled

Each was found by the corpus, not by inspection, and each is a consequence of
the same fact: **an IR scope is not a Python scope.** `backend-go` never meets
any of them, because its `Let` is an IIFE and every IR scope becomes a real
target scope for free.

1. **Sibling IR scopes flatten into one Python function scope.** A local is
   named from its de Bruijn level, which the optimizer makes unique only
   *within* a scope, so two independent `Let`s that each open at level 2 both
   want `v2` — and the second silently rebinds a name a closure over the first
   had already captured. `Test.Generic` does this three times in one `Show`
   instance. Uniqueness is therefore enforced against every local emitted in the
   module; renaming is always safe because references resolve through a map, not
   by reconstructing the name.
2. **Top-level bindings share module scope.** The same collision one level up:
   two top-level bindings that each open a `Let` at level 0 both emit `v0` at
   module scope. Each binding's statements are confined to an `_init_` function,
   called immediately.
3. **Generated loop dispatchers are module-level `def`s.** Two loop groups whose
   first parameter shares a level would both be `_loop0`. Loop names come from
   the module-wide fresh counter.
4. **Generated names and user identifiers share one namespace.** A local is
   `v3_x`, and nothing stops a module from having a top-level binding *called*
   `v3_x` — the local shadows it, and a reference to the top-level one from
   inside that function silently reads the local. `backend-go` is immune only
   because its top-level names are module-qualified (`Data_Foo_v3_x`); Python's
   are bare. Every generated name therefore carries a reserved `_ps_` prefix
   that `pyIdent` escapes user identifiers out of — the same mechanism the
   module aliases already use, and for the same reason. This one was fixed by
   analogy rather than by a failing test, which is the only reason it is not a
   fifth entry in the corpus's list of finds.

### The remaining frontier: join points

> **Progress (2026-07-31): implemented, here and on Jurist's `backend-jl`.**
> The sketch below was right about the shape and incomplete about the cost. A
> join point does become another member of the dispatch group — but folding it in
> means *lifting it out of the member it was written inside*, and it may have
> captured variables from there. `TCOMutRec`'s `tco4` has `g y' = f (x + 2) y'`
> reading `f`'s parameter `x`; a jump leaves the frame, so `x` has to travel too.
>
> The fix is one idea: **make the register file keyed by LOCAL rather than by
> position** — one slot per distinct local any branch binds, being every member's
> parameters plus the free variables the join points captured. `x` then gets one
> slot whether it arrives as `f`'s parameter or as `g`'s capture. Every branch
> binds every slot on entry, which costs a few dead assignments and buys the
> invariant the whole thing rests on: at any jump site every slot is in scope, so
> a captured variable survives an arbitrary chain of jumps.
>
> Free variables are filtered by de Bruijn level against the group's own
> parameters. Anything bound further out is already reachable lexically — the
> dispatch `def` is emitted *inside* the enclosing scope — and putting it in a
> register would shadow it. `tco3`'s `g` reads `y0` and `j` from two scopes up and
> must not.
>
> One Python-specific trap: the register file has to be bound **once**, with every
> branch reusing those names. `bindLocal` enforces module-wide uniqueness (see the
> four hazards above), so binding per branch would rename the second branch's copy
> of a slot away from the first's. The Julia lane does not have this problem,
> because there each `let` is its own scope.
>
> Measured on `TCOMutRec`'s four positive cases, byte-identical to the JavaScript
> reference at depth 100,000, and still correct at 1,000,000 — flat stack, not
> merely deep:
>
> ```
> tco1 2000000   tco2 2000000   tco3 2499997   tco4 2000000
> ```
>
> `tco3` is the case that makes the design earn its keep: its `g` is *both* a
> self-loop and a join, so it has to be a branch that can jump to itself and to
> `f`.
>
> **`TCOMutRec` as a whole still fails, and now for a reason that is not ours.**
> The test also asserts that four *non*-TCO-able shapes MUST overflow
> (`assertThrows \_ -> ntco2 100000`), and the optimizer inlines `ntco2`'s and
> `ntco4`'s helper away, turning each into a plain self-tail-loop that completes.
> Confirmed independently on `backend-jl` — a different lowering over the same
> optimizer — which also completes `ntco2`, while `purepy` (the oracle, no
> optimizer) overflows exactly as the test demands. The corpus now reports
> `Assertion failed: An error should have been thrown` rather than a
> `RecursionError`, which is the failure saying so itself.
>
> That puts `TCOMutRec` where Gnomon's half of it already sits: the
> `assertThrows` assertions describe a *runtime and optimizer* property rather
> than PureScript semantics, and belong in the divergence ledger next to `INT64`
> and `ASTRAL`.

~~`TCOMutRec` still fails, and the reason is precise rather than vague.~~ Its `tco1`
defines `g` in a `where` *inside* `f`, so the optimizer marks each a separate
self-loop; the cross-calls between them stay ordinary stack calls, and 100,000
of those exhaust CPython. The optimizer already computes what is needed —
`TcoRole.joins` — and `backend-py` currently reads only `isLoop`. Consuming
`joins` means carrying backend-es's `BlockMode` (a TCO scope stack plus a join
set) through the emitter. That is the next slice, and it is a real one.

The lowering, though, should **not** copy backend-es's. There a join point is an
ordinary function that assigns the enclosing loop's registers and returns, and
the caller then `continue`s — which works because JavaScript's loop variables
are mutable state in an enclosing closure. `_tco_run`'s registers are function
*parameters*, precisely so each iteration gets its own frame, so nothing can
reach in and assign them. The shape that does fit is already built: a join point
is a local binding all of whose calls are tail calls from inside the loop, so it
can simply become **another member of the same dispatch group** — one more index
in the branch register, and a tail call to it is `return (1, (n, …))` like any
other. The mutual-recursion machinery is the join machinery.

Worth recording precisely because the comparison is misleading: `backend-go`
*passes* `TCOMutRec`'s four `tco*` assertions without implementing joins at all.
It is not trampolining them — Go's goroutine stacks simply grow to about a
gigabyte, so 100,000 frames of honest recursion survive. Python's 10,000-frame
limit makes the gap visible. **The Go lane's green here measures the runtime,
not the lowering**, which is exactly the kind of claim differential conformance
exists to keep us honest about.

## Alternatives considered

**Replace `purepy` with `backend-py`.** Rejected: it discards the oracle, and
with it the only mechanism that can catch a codegen bug neither author thought
to test. Two lanes that must agree is the whole method.

**Hand-port `Codegen/Tco.purs` into `purepy` (Haskell).** Rejected as the
family-wide answer: three ports of one analysis, each free to drift from a
frontier the corpus asserts byte-for-byte. It remains available for `purepy`
alone if the oracle ever needs to close the same gap.

**Fork the runtime into `backend-py/`,** as Gnomon did. Rejected on measured
evidence — see Decision, point 2.

**Port `purepy`'s expression-oriented emitter** (0002) rather than writing a
statement-oriented one. Rejected: it would have inherited the paren-nesting wall
and the lambda-lifting pass built to survive it, and `BigFunction` would still
fail. The IR is already flat enough that statements are the simpler target.
